# 阶段 4B.5 收口审查：后端国际化底座代码质量、模块边界与链路完整性复核

## 一、审查目标

在**不扩展多语言能力**、**不进入 4C** 的前提下，对 4B.5 初版实现的结构、边界、链路及与设计文档一致性做专项复核；对确定性的小问题可直接收敛。

**依据**：  
《后端多语言支持策略设计 V1》《后端包结构与命名规范 V1》《阶段 4A-Admin 认证体系详细设计》及 `services/website-services/README.md`。

---

## 二、审查范围

- `common`：`ErrorCode`、`BusinessException`、`ApiResponse`
- `infra`：`I18nProperties`、`I18nConfig`、`LocalizedMessageService`/`Impl`、`MessageKeys`、`ApiResponseMessageLocalizationAdvice`
- `auth` / `admin` / `site-app`：bundle、Handler、Security 入口、`AdminLoginRequestDto`、相关测试
- 链路：`BusinessException`、Validation、Security 401/403、扩展语言的可操作性

## 三、总体结论

整体设计**与设计文档对齐**，分层（`common` 无 Spring、`infra` 解析、`auth`/`admin` 分包文案）清晰，**未发现**需要再拆抽象层或重复的 `MessageSource` 包装链路。本轮针对 **Advice 隐性风险**与 **site-app 过早依赖**做过**最小收敛**后，更可维护。

---

## 四、common 模块审查结果

| 项 | 结论 |
| --- | --- |
| **ErrorCode** | 仅有 `code` + `messageKey`，无解析逻辑，符合文档。 |
| **BusinessException** | 仅存 `code` / `messageKey` / `messageArgs`，不依赖 Spring/infra；`super(message)` 传 key 属可接受的 Runtime 语义。 |
| **构造器数量** | `ErrorCode` / `(int,key,args)` 两类入口，语义清楚；与阶段 4A 已定「同语义码、不同业务 key」一致。 |
| **ApiResponse.success** | 因 `common` 不能绑定 `MessageSource`，成功消息仍为 key → 由 infra 切面补译是当前工程约束下的**务实折中**；见下文 Advice 收窄说明。 |

**依赖**：未发现 `common` 反向依赖 `infra`。

## 五、infra（国际化底座）审查结果

### 5.1 I18nProperties

- 模型简练：`default-locale`、`supported-locales`；
- `_`→`-`、`Locale.forLanguageTag` + `language` 非空的校验够用，**未发现**无效过度封装。

### 5.2 I18nConfig

- 使用 **`AcceptHeaderLocaleResolver`** + `supportedLocales`/defaultLocale，与 Spring Boot 能力一致，**非**重复造轮。

### 5.3 LocalizedMessageService

- 三路重载：`无请求 Locale`/`显式 Locale`/`HttpServletRequest`（Security）分工明确；
- Fallback：`MessageSource` 负责 bundle 链回日文；日文仍缺 key → 返回 key + warn，集中在一处。

### 5.4 MessageKeys

- **仍有必要**：在不向 `ApiResponse` 引入类型标记的前提下，为 Advice 提供**低成本**启发式；
- **与业务 key 常量表无重复**：未引入各模块枚举式 key 常量，避免第二套真值源。

### 5.5 ApiResponseMessageLocalizationAdvice（结论）

**保留**，理由：`ApiResponse.success()` 无法在 `common` 内本地化，由各 Controller 手写 `LocalizedMessageService` 会重复噪声。

**风险与收敛（已落地）**：原实现对**任意 code**只要 message「像 key」即翻译，虽有「错误体通常为自然语言」的经验保障，仍存在理论上的隐性耦合。已将切面**收窄为：`code == ErrorCode.SUCCESS`（0）** 后再做 `MessageKeys` 判断；《后端多语言支持策略设计 V1》已补充 **§5.1** 说明触发条件与边界。

## 六、auth / admin / site-app 审查结果

| 项 | 结论 |
| --- | --- |
| **分包** | `common` 通用、`auth` 认证与安全通用、`admin` 专属，符合前缀约定。 |
| **key 冲突** | 未发现同 key 多模块并行维护冲突；`admin.auth.refresh.invalid` 与 `auth.unauthorized` 日文文案相同属于**语义不同、文案复用**，可接受。 |
| **Admin Handler / Security** | 统一走 `LocalizedMessageService`，无第二套手写 `getMessage`。 |

| **`auth.token.*`** | Java 侧未引用，属未使用占位；已从三语 **`auth`** bundle **删除**，减少「死翻译」表面积；日后 JWT 粒度错误再回到资源文件即可（无需改枚举语言范围）。 |

## 七、链路完整性复核

### 7.1 BusinessException

业务 `throw BusinessException(...)` → `GlobalExceptionHandler` → `LocalizedMessageService` → `MessageSource` → `ApiResponse.fail(已本地化)`；**Advice 不再作用于非零 code**，无二次解析；漏网暴露 raw key：仅当属 `SUCCESS` code 的假成功体（应避免）。

### 7.2 Validation（Admin）

`{admin.auth.*}` → Bean Validation → Spring `MessageSource`（Locale 取自请求上下文）→ Handler 使用 `fieldError.defaultMessage`（已是自然语言）→ Advice 不改写非零 **code**。**无双重 MessageSource** 在同一响应上叠加。

### 7.3 Security 401 / 403

手写 JSON：`LocalizedMessageService.getMessage(request, key)` → 已本地化正文；HTTP 状态与 `ApiResponse` 形状不变。**篡改 JWT 仍走 WWW-Authenticate / invalid_token** 的既有路径未改代码路径。

### 7.4 新增 ko-KR

仍符合「**仅**配置 + 三模块追加 `messages_ko_KR.properties` + 翻译 key」范式；切面与 Handler **无语言枚举硬编码**。

## 十、仍需人工拍板的非阻塞项

| 议题 | 说明 |
| --- | --- |
| **MessageKeys 启发式边界** | 极端情况下「成功 message 必须为 `aaa.bbb` 形原文」仍会命中切面；需在业务侧规避或不用 `success`+该字面形态。体量极小，一般不展开。 |
