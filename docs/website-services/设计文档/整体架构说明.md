# my-website 整体架构说明

本文档描述 `my-website` 仓库的整体架构、子系统职责与本地开发启动顺序。更细的模块设计请参考各子目录下的专项文档。

## 1. 项目定位

`my-website` 是一个多站点网站合集平台，目标是用一套平台能力支持多个行业站点，例如汽车维修、蛋糕烘焙，后续也可以扩展到美容院、诊所、中古车店等场景。

平台分为三类能力：

- 前台站点：面向访客，展示行业站点内容并提供咨询、预约等入口。
- 后台管理：面向运营/管理人员，管理站点、模板、配置、内容、文件、预约与数据。
- 后端服务：统一网关、后台 API、前台 API、基础设施接入、AI/Agent 客户端与未来业务模块。

## 3. 子系统职责

### 3.1 apps/admin-web

后台管理前端，负责多站点平台的管理界面。

主要职责：

- 站点管理
- 模板与页面配置
- 内容、文件、预约管理
- AI 知识库与 Prompt 管理
- 数据统计与系统设置

专项文档：

- `docs/admin-web/架构设计.md`
- `docs/admin-web/API设计.md`

### 3.2 apps/site-web

前台站点集合目录，按行业拆分不同前台应用。

当前包含：

- `car-web`：汽车维修行业站点
- `cake-web`：蛋糕烘焙行业站点

前台站点主要通过后端 `gateway` 访问前台 API，后续也可接入 AI 咨询、预约、站点公开配置等能力。

### 3.3 services/website-services

Java 后端多模块工程，当前是后端主干服务。

核心运行模块：

- `gateway`：统一 API 网关，端口 `8080`
- `admin`：后台管理 API，端口 `8081`
- `site/site-app`：前台站点 API，端口 `8082`

基础与业务模块：

- `common`：通用响应外壳、错误码（**`messageKey` 驱动的 `ErrorCode`**）、异常（**`BusinessException` + args**）与分页模型；**不**下沉任何业务 REST Request/Response（边界见：[后端包结构与命名规范 V1](./后端包结构与命名规范V1.md)）。
- `infra`：PostgreSQL、Redis、MinIO/S3 接入；**系统消息国际化底座**（`Accept-Language`、默认 `ja-JP`、`LocalizedMessageService` 等，详见 [后端多语言支持策略设计 V1](./后端多语言支持策略设计V1.md)）。
- `auth`：公共认证基础能力，不承载具体用户表
- `agent`：未来对接 AI/Agent 运行服务的 Java 客户端层
- `config`：网站配置业务能力预留
- `site/site-core`：前台站点核心能力与统一 site 用户体系
- `site/site-car`：汽车站点业务模块
- `site/site-cake`：蛋糕站点业务模块

专项文档：

- [`后端包结构与命名规范 V1`](./后端包结构与命名规范V1.md)

### 3.4 services/agent-service

Node.js + TypeScript 的 AI/Agent 编排服务。当前仍处于 mock/骨架阶段，后续可承载模型调用、Prompt 编排、SSE 流式响应与业务服务转调。

未来 Java 后端的 `agent` 模块会作为客户端层调用该服务。

## 4. 后端调用关系

推荐请求路径：

```text
admin-web ─┐
           ├──> website-services/gateway:8080 ──> admin:8081
site-web  ─┘                                └──> site-app:8082
```

内部后续关系：

```text
site-app / admin
  ├── infra  -> PostgreSQL / Redis / MinIO
  ├── auth   -> 公共认证基础能力
  ├── config -> 网站配置能力
  └── agent  -> services/agent-service
```

当前阶段不引入注册中心、服务发现、消息队列或复杂网关鉴权。`gateway` 只做统一入口、CORS、基础 request-id 与路由。

## 5. 数据与用户模型边界

后台用户体系归 `admin`：

- `admin_user`
- `admin_role`
- `admin_permission`
- `admin_user_role`
- `admin_role_permission`

前台用户体系归 `site/site-core`：

- `site_user`
- `site_user_profile`
- 可选扩展 `site_user_auth`

前台多站点用户统一使用 `site_user`，通过 `site_id` 或 `site_code` 隔离不同站点。不要为不同业务站点分别创建 `car_user`、`cake_user`。

`auth` 只保留公共认证抽象，例如 Token/JWT、认证上下文、当前登录用户抽象，不承载具体用户表。

## 6. 本地基础设施

### 6.1 `website-services` 与 Docker Compose

**`services/website-services/docker-compose.yml` 当前仅包含 PostgreSQL 与 Redis**。  
**MinIO / AIStor 暂不并入该 Compose**，继续在 Docker/WSL 中 **单独部署**（或使用既有实例）。**阶段 4B Admin 认证**的主线依赖为 **PostgreSQL + Redis**，不因对象存储增加 Compose 前置。**MinIO** 计划在 **媒体资源与文件上传阶段**再纳入业务主线。

### 6.2 常见端口（含按需另行部署的服务）

本地后端常用端口：

- PostgreSQL：`localhost:5432`
- Redis：`localhost:6379`
- MinIO / AIStor API：`http://localhost:9000`（**非上述 Compose 默认项**，按需拉起）
- MinIO / AIStor Console：`http://localhost:9001`

建议先启动本地基础设施，再启动 Java 后端服务。否则应用可启动，但 actuator health 中数据库或 Redis 可能显示 `DOWN`。

## 7. 推荐启动顺序

1. 启动 WSL + Docker 本地基础设施。
2. 启动 `services/website-services` 后端：

```bash
cd services/website-services
mvn clean install -DskipTests
mvn -pl admin -am spring-boot:run
mvn -pl site/site-app -am spring-boot:run
mvn -pl gateway -am spring-boot:run
```

3. 启动前端应用：

```bash
cd apps/admin-web
pnpm install
pnpm dev
```

```bash
cd apps/site-web/car-web
pnpm install
pnpm dev
```

```bash
cd apps/site-web/cake-web
pnpm install
pnpm dev
```

`gateway` 可以最先启动，也可以在 `admin` 和 `site-app` 之后启动。联调时建议先启动 `admin/site-app`，再启动 `gateway`，这样访问网关路由时后端目标服务已经就绪。
